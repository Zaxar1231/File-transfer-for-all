# Архитектурные решения (этап 0)

Документ фиксирует выбор стека и зависимостей. Он сверен с дорожной картой из 9 этапов;
статус каждого этапа — в конце.

## Язык бэкенда: Python вместо Go или Rust

Дорожная карта предлагает сравнить Go и Rust. Сравнение ниже, но выбран третий вариант:
оставить Python, на котором уже работают ядро, семь протоколов, GUI и CLI.

| Критерий | Go | Rust | Python (выбран) |
|---|---|---|---|
| Сетевые библиотеки | отличные: `x/crypto/ssh`, `pkg/sftp`, `go-smb2`, AWS SDK, `pion/webrtc` | хорошие: `russh`, `ssh2`, `smb`/`pavao` слабее, `webrtc-rs` | отличные: paramiko, asyncssh (SSH-сервер), smbprotocol, boto3, zeroconf |
| Размер бинарника | 10–30 МБ, один файл | 5–15 МБ, один файл | 60–120 МБ вместе с Flutter-оболочкой и интерпретатором |
| Кроссплатформенность | Windows, macOS, Linux; Android только через gomobile | то же, Android через cargo-ndk | Windows, macOS, Linux, Android, iOS одной сборкой Flet |
| Скорость разработки | средняя | низкая | высокая |
| Общий код с GUI | нужен мост (FFI/gRPC) к Flutter/Qt | нужен мост | GUI и ядро — один процесс, один язык |

Почему Python: переписывание на Go или Rust дало бы меньший бинарник, но потеряло бы
готовые и протестированные протоколы и потребовало бы моста между ядром и интерфейсом на
каждой платформе. Узкие места передачи (хеширование, шифрование, TLS, SSH) уже выполняются
в C/Rust внутри библиотек (`hashlib`, `cryptography`, `ssl`), так что Python здесь
управляет потоком данных, а не считает байты. Если размер бинарника станет критичным,
ядро можно вынести в отдельный Go-сервис, сохранив интерфейс `Transport`.

## GUI: Flutter через Flet

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Flutter (Flet)** — выбран | Material 3 нативно, Android/iOS/десктоп из одного кода, ядро на Python в том же процессе | бинарник крупнее, Flet 1.0 молодой |
| Tauri | маленький бинарник, веб-UI | мобильные платформы в бете, ядро пришлось бы писать на Rust |
| Qt | зрелый, нативный вид | Material You вручную, мобильная сборка сложная, лицензия LGPL/коммерческая |
| Electron | огромная экосистема | 150+ МБ, нет мобильных платформ |

## Протоколы: что пишем сами, что берём готовым

| Протокол / функция | Реализация |
|---|---|
| Локальная ФС, HTTP(S), WebDAV | своё, поверх стандартной библиотеки |
| FTP/FTPS | `ftplib` (stdlib) |
| SFTP-клиент | paramiko |
| SSH/SFTP-сервер для PuTTY | asyncssh |
| SMB 2/3 | smbprotocol |
| S3 и совместимые | boto3 |
| Облака (Google Drive, Dropbox, Яндекс.Диск, OneDrive и ещё 50+) | внешняя программа **rclone** |
| Обнаружение в LAN | zeroconf (mDNS/DNS-SD) |
| Прямая передача между устройствами | свой протокол поверх HTTPS (по образцу LocalSend) |
| Передача через NAT | внешняя программа **croc** (relay, PAKE-коды); WebRTC не берём, см. ниже |
| QR-коды | qrcode |
| Целостность | SHA-256 на файл и на блок 4 МиБ (`hashlib`) |
| Шифрование | TLS с закреплённым отпечатком между устройствами; age (pyrage) для шифрования файлов перед загрузкой в облако |
| NFS | монтирование средствами ОС (путь виден как локальный); своего клиента нет: в Python нет зрелой библиотеки |

**WebRTC.** Для работы через NAT нужен сигнальный сервер и TURN-релей, которые кто-то
должен держать. croc решает ту же задачу готовым публичным релеем и шифрованием по коду,
поэтому вместо WebRTC используется он.

## Зависимости

Обязательные (`pyproject.toml`): flet, paramiko, boto3, smbprotocol, asyncssh, zeroconf,
segno (QR-коды без Pillow), cryptography (сертификат устройства), tomli (Python < 3.11),
tomli-w.

Опциональные: pyrage (шифрование age), внешние программы rclone и croc — приложение
находит их в `PATH` и предлагает установить, если их нет.

### Этап 3: прямая передача

`fta.lan.direct` — небольшой HTTPS-протокол: `POST /api/offer` со списком файлов
(относительные пути, размеры, время, права) → пользователь получателя принимает или
отклоняет → `PUT /api/file` по одному файлу в `имя.fta-part`, переименование после
полного приёма, SHA-256 сверяет отправитель → `POST /api/done` проставляет время папкам.
Пути проверяются (`..`, абсолютные, `C:`), существующие имена не перезаписываются
(`имя (1)`). Сертификат самоподписанный, закрепляется по SHA-256; отпечаток приходит
через mDNS (`_fta._tcp`) или QR-код (`fta://host:port/?fp=…`). Идентификатор сеанса
секретный: по нему прерванная передача продолжается без повторного вопроса.

### SSH-терминал

`fta.terminal.SshTerminal`: paramiko открывает оболочку с `TERM=xterm-256color`,
pyte (эмулятор VT100/xterm на чистом Python) превращает поток в экран, интерфейс
рисует его прогонами одного стиля (`Run`). Текст набирается в строке ввода (так
работают экранная клавиатура телефона и вставка), остальные клавиши идут с аппаратной
клавиатуры или с панели клавиш. Ключи хостов — `fta.core.hostkeys`: неизвестный ключ
поднимает `UnknownHostKey` с отпечатком, пользователь подтверждает, ключ пишется в
`known_hosts` приложения; изменившийся ключ — `HostKeyChanged`. Тесты гоняют терминал
против настоящего bash в псевдотерминале (`tests/bash_ssh_server.py`).

### Этап 4: облака и NFS

Облака — через rclone, а не собственные клиенты к каждому API: rclone уже умеет 70+
хранилищ, OAuth и их ограничения. `fta.tools.rclone` находит программу (папка приложения,
затем PATH), ставит официальную сборку с проверкой `SHA256SUMS`, создаёт облака в
собственном `rclone.conf` приложения и видит облака из обычного конфига пользователя.
`rclone://имя/путь` — транспорт: `lsjson` для списков, `rcat` для загрузки (поток идёт
через приложение, поэтому прогресс точный), `cat --offset` для скачивания с докачкой.

NFS отдельным транспортом не сделан: клиент NFS в пространстве пользователя (libnfs)
требует нативной сборки под каждую платформу, а смонтированный системой ресурс уже
доступен приложению как обычная папка, со всеми функциями копирования и проверки.

### Этап 5: безопасность

* `fta.crypto.age` — собственная реализация формата age v1 на `cryptography`
  (scrypt и X25519, STREAM на ChaCha20-Poly1305 блоками по 64 КиБ, HMAC заголовка,
  bech32-ключи). Отдельный нативный пакет (pyrage) не нужен — это важно для Android.
  Совместимость проверяет тест против официальной утилиты `age`.
* `fta.lan.shares` — ссылки `https://адрес:порт/s/<128 бит>` на том же HTTPS-сервере,
  что принимает файлы. Одноразовая ссылка «сгорает» до отправки первого байта, поэтому
  два одновременных клика не скачают файл дважды.
* `fta.crypto.totp` — RFC 6238 (проверено векторами из приложения B), окно ±30 с,
  повтор кода запрещён. SSH-сервер с 2FA принимает пароль только через
  keyboard-interactive вместе с кодом; вход по ключу остаётся однофакторным.
* `tests/test_fuzz.py` — свойства для любых входов. Фаззинг уже нашёл и закрыл две
  ошибки: повреждённый base64 в заголовке age давал `binascii.Error` вместо понятной
  ошибки, а предложение передачи `null` роняло обработчик без ответа.

### Этап 6: оптимизация

* Дельта без программы на сервере. rsync сравнивает блоки на обеих сторонах и требует
  себя на сервере; у SFTP/SMB такого нет. Поэтому `fta.core.sync` хранит манифест того,
  что сам записал: хеши блоков по 4 МиБ, размер и время копии. Если копию с тех пор никто
  не трогал (размер и время совпадают), изменённый файл патчится на месте
  (`Transport.patch`: SFTP, локальные, memory), остальное отправляется целиком.
* Лимит скорости — одно «ведро токенов» на процесс (`fta.core.throttle`). Счётчик прогресса
  есть у всех транспортов, поэтому лимит работает для любых протоколов и для «Рядом».
* Планировщик проверяет расписания раз в 20 секунд и ставит задания в общую очередь
  (с паузой, повторами и журналом). Время последнего запуска хранится в `config.toml`.
* Портативный режим — папка `fta-data` рядом с программой (до трёх уровней вверх, чтобы
  найти её и рядом с `.app` на macOS).
