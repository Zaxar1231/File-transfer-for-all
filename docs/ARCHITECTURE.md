# Архитектурные решения (этап 0)

Документ фиксирует выбор стека и зависимостей. Он сверен с дорожной картой из 9 этапов;
статус каждого этапа — в конце.

## Язык бэкенда: Python вместо Go или Rust

Дорожная карта предлагает сравнить Go и Rust. Сравнение ниже, но выбран третий вариант:
оставить Python, на котором уже работают ядро, семь протоколов, GUI и CLI.

| Критерий | Go | Rust | Python (выбран) |
|---|---|---|---|
| Сетевые библиотеки | отличные: `x/crypto/ssh`, `pkg/sftp`, `go-smb2`, AWS SDK, `pion/webrtc` | хорошие: `russh`, `ssh2`, `smb`/`pavao` слабее, `webrtc-rs` | отличные: paramiko, asyncssh (SSH-сервер), smbprotocol, boto3, zeroconf |
| Размер бинарника | 10–30 МБ, один файл | 5–15 МБ, один файл | 60–120 МБ вместе с Flutter-оболочкой и интерпретатором |
| Кроссплатформенность | Windows, macOS, Linux; Android только через gomobile | то же, Android через cargo-ndk | Windows, macOS, Linux, Android, iOS одной сборкой Flet |
| Скорость разработки | средняя | низкая | высокая |
| Общий код с GUI | нужен мост (FFI/gRPC) к Flutter/Qt | нужен мост | GUI и ядро — один процесс, один язык |

Почему Python: переписывание на Go или Rust дало бы меньший бинарник, но потеряло бы
готовые и протестированные протоколы и потребовало бы моста между ядром и интерфейсом на
каждой платформе. Узкие места передачи (хеширование, шифрование, TLS, SSH) уже выполняются
в C/Rust внутри библиотек (`hashlib`, `cryptography`, `ssl`), так что Python здесь
управляет потоком данных, а не считает байты. Если размер бинарника станет критичным,
ядро можно вынести в отдельный Go-сервис, сохранив интерфейс `Transport`.

## GUI: Flutter через Flet

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Flutter (Flet)** — выбран | Material 3 нативно, Android/iOS/десктоп из одного кода, ядро на Python в том же процессе | бинарник крупнее, Flet 1.0 молодой |
| Tauri | маленький бинарник, веб-UI | мобильные платформы в бете, ядро пришлось бы писать на Rust |
| Qt | зрелый, нативный вид | Material You вручную, мобильная сборка сложная, лицензия LGPL/коммерческая |
| Electron | огромная экосистема | 150+ МБ, нет мобильных платформ |

## Протоколы: что пишем сами, что берём готовым

| Протокол / функция | Реализация |
|---|---|
| Локальная ФС, HTTP(S), WebDAV | своё, поверх стандартной библиотеки |
| FTP/FTPS | `ftplib` (stdlib) |
| SFTP-клиент | paramiko |
| SSH/SFTP-сервер для PuTTY | asyncssh |
| SMB 2/3 | smbprotocol |
| S3 и совместимые | boto3 |
| Облака (Google Drive, Dropbox, Яндекс.Диск, OneDrive и ещё 50+) | внешняя программа **rclone** |
| Обнаружение в LAN | zeroconf (mDNS/DNS-SD) |
| Прямая передача между устройствами | свой протокол поверх HTTPS (по образцу LocalSend) |
| Передача через NAT | внешняя программа **croc** (relay, PAKE-коды); WebRTC не берём, см. ниже |
| QR-коды | qrcode |
| Целостность | SHA-256 на файл и на блок 4 МиБ (`hashlib`) |
| Шифрование | TLS с закреплённым отпечатком между устройствами; age (pyrage) для шифрования файлов перед загрузкой в облако |
| NFS | монтирование средствами ОС (путь виден как локальный); своего клиента нет: в Python нет зрелой библиотеки |

**WebRTC.** Для работы через NAT нужен сигнальный сервер и TURN-релей, которые кто-то
должен держать. croc решает ту же задачу готовым публичным релеем и шифрованием по коду,
поэтому вместо WebRTC используется он.

## Зависимости

Обязательные (`pyproject.toml`): flet, paramiko, boto3, smbprotocol, asyncssh, zeroconf,
qrcode, tomli (Python < 3.11), tomli-w.

Опциональные: pyrage (шифрование age), внешние программы rclone и croc — приложение
находит их в `PATH` и предлагает установить, если их нет.
